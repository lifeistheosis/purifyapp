# PRD Patch · Community Feedback Cycle, May 26 2026

Source: Discord pre-launch testers. Four feature requests, formalized below against the current Purify codebase (`lib/saints/saints.ts`, `data/saints/*`, `lib/calendar/*`, Supabase `profiles`/`bookmarks`/`annotations`).

---

## 🔍 1. Topical Patristic & Apologetics Index

**User Intent.** Enquirers, catechumens, and lay apologists need to type a doctrinal term ("the Trinity", "Filioque", "soul sleep", "icons") and get one screen with (a) a short Orthodox definition of the term, (b) the patristic citations that confess it, and (c) where applicable, the patristic citations that refute its opposite. The interaction model is a research tool, not a chat — the user wants quotable primary text in two clicks.

**Data Schema (Supabase + repo).** Avoid duplicating any patristic text. The site already stores every patristic block once in `data/saints/{slug}/{work}.json` as numbered sections with paragraphs and the `topics: string[]` field on each `Work`. Build a thin topics layer on top:

- **Repo, source-of-truth (no DB):** new `data/topics/{topic-slug}.json` files with shape `{ slug, title, definition, tradition?: string, citations: { saintSlug, workSlug, sectionN, paragraphIndex, stance: "affirms" | "refutes", gloss?: string }[] }`. Editorial work, version-controlled, public-domain only.
- **Supabase, derived index:** materialized view `topic_citation_index` (read-only, populated by a build-time `scripts/build-topic-index.mjs`) joining the JSON above with a tsvector over the paragraph text so a user-typed query can either (i) match a curated topic slug or (ii) full-text rank across the corpus when no curated topic exists. Storing the index in Postgres rather than shipping the whole corpus to the browser keeps page weight bounded and supports the "type something we didn't curate" path.
- **Reuse, don't replicate:** the `Work.topics` array stays primary metadata; the new files just deep-link into specific paragraphs.

**UI/UX Strategy.** Mirror the contemplative chrome already established on `/saints/[slug]/[work]`. Route `/topics/[topic-slug]`:

- **Hero:** display-serif H1 with the topic name; one-paragraph Orthodox definition in body serif; a small gold eyebrow `TOPICAL INDEX`.
- **Two columns on desktop, stacked on mobile:** "Confessed by the Fathers" (gold rule) and "Refuted by the Fathers" (cinnabar/rubric rule, matching the calendar's two-color liturgical printing palette established in v5.2). Hide the refuting column entirely when no citations exist — never render an empty rubric.
- **Citation card:** saint icon at 32px, attribution line, paragraph as a pull-quote, source link to `/saints/{slug}/{workSlug}#sN`. No accordions; the page is meant to be read top to bottom.
- **Search affordance:** topical search lives behind a single input at `/topics`. Curated topic hits render the structured page above; uncurated queries render a flatter ranked list with a small note: *"No curated index for this term yet. Showing the closest matches from the Fathers."* This is the honesty pattern the site already uses on `/calendar` (surfacing both reckonings without arbitrating).
- **Reverence guardrails:** no upvotes, no "popular topics," no streak/gamification. The page is a reference; treat it like one.

**Open question.** Editorial process for the curated topic files (who writes, who reviews) needs to be settled before the schema ships. Suggest a minimal `docs/topics-editorial.md` analogous to the existing source attribution pattern.

## 🌐 2. Internationalization (i18n) Roadmap

**Scope.** Three asks (Greek, Russian, Spanish) are not the same problem. Split into two tracks:

- **Track A — UI chrome localization (Spanish first).** Translate navigation, button labels, eyebrows, error strings, FAQ, About, prayer-rule scaffolding. Texts themselves (Scripture, Fathers) stay in their published languages. Roughly ~1,200 strings.
- **Track B — Liturgical/textual localization (Greek + Russian).** Surface the Scriptures and prayers in Greek and Slavonic/Russian. This is a content acquisition problem more than an engineering one: each language needs a vetted public-domain corpus (Patriarchal Greek Bible for NT Greek, Synodal Russian for Scripture, Church Slavonic prayer books) and an editorial pass for the prayer rules' wording.

Phase plan:

1. **Phase 1 (engineering only).** Lay i18n routing and string extraction so Spanish UI chrome can ship behind a `/es` locale prefix. No content yet.
2. **Phase 2 (Spanish ships).** Translated chrome live; banner on `/es` naming the texts that remain in English.
3. **Phase 3 (Greek liturgical).** Add a Greek Bible reader column toggle alongside the existing Nestle 1904 interlinear (the LXX OT is already in Greek; the NT primary Greek is already there — this is about NT Greek-only display and Greek UI chrome at `/el`).
4. **Phase 4 (Russian).** Synodal Bible + Slavonic prayer set at `/ru`. Largest content lift; budget accordingly.

**Technical Execution.**

- **Next.js routing.** Use the App Router's locale segment pattern (`app/[locale]/(app)/...`) over `next-intl` to keep the static-export-friendly behavior the PWA depends on. Middleware reads `accept-language` once on first visit, persists the chosen locale to a `purify_locale` cookie, and serves matching static segments thereafter.
- **String catalog.** `lib/i18n/messages/{locale}.json` flat-key catalogs. Server components read via `getMessages(locale)`; client components receive their slice via a single `MessagesProvider` mounted once in the locale layout. Avoid per-component imports — they tank the build graph.
- **PWA caching.** Service worker (added in v6.1) already does `StaleWhileRevalidate` on static assets; add locale catalogs to that bucket so a returning Spanish reader on a flaky connection still gets their UI.
- **Render-specific note.** Render's static asset pipeline handles locale-prefixed routes fine; no extra config. The `revalidate = 3600` ISR on home and `/calendar` works per-locale automatically once the segment is in place.
- **Right-to-left:** out of scope for these three languages; defer.

**Open question.** Translation labor: in-house, professional translation contract, or community contributions through a moderated workflow? Each has different governance implications for a religious product.

## 📚 3. Content Ingestion: St. Theophylact's Commentaries

**Ingestion Strategy.** Treat Theophylact like the existing Chrysostom-on-John pipeline (`scripts/ingest-chrysostom-john.mjs`), not as a copy-paste job.

- **Source selection.** The Azbyka.ru source the tester linked is Russian, and its translation is modern. For shipping in English under Purify's public-domain discipline, the workable starting point is the 19th-century English translation of the *Explanation of the Holy Gospel According to St. Matthew / Mark / Luke / John* — verify edition and translator are pre-1929 US PD / pre-life+70 in source country before ingest. If a clean PD English Theophylact corpus cannot be confirmed, a licensed edition would need negotiation; we should not ship a translation we can't attribute.
- **Pipeline shape.** Mirror the Chrysostom ingest:
  1. Plaintext fetch into `scripts/lib/theophylact-source.mjs` with footnote/page-marker scrubbing.
  2. Slice by Gospel chapter; within each chapter, split on the verse-keyed "Ver. N" markers Theophylact's translations universally use.
  3. Emit two artifacts per work: `data/saints/theophylact-of-ohrid/explanation-of-matthew.json` (the full work for the saint profile) and per-chapter `data/commentary/matthew/{chapter}.json` patches keyed to verse.
  4. Sanity check: any chapter with >15% untagged verses fails the build (same gate as Chrysostom's import).
- **Add the saint.** New entry in `lib/saints/saints.ts` (slug `theophylact-of-ohrid`, feast Dec 31, byname "The Bulgarian", epithet "Archbishop of Ohrid · Explainer of the Gospels"). Author-name mappings in `lib/saints/icons.ts`. Icon file `public/saints/icons/theophylact-of-ohrid.jpg` once supplied.
- **The Azbyka structural link** is a Russian-language reading aid — not redistributable text, but worth a one-line *Further reading* link on the saint profile pointing at the Azbyka page, treated the same way `/about` already credits the publishers of the licensed modern translations.

**Reader Integration.** No new chrome required.

- The saint profile renders out of the existing `app/(app)/saints/[slug]/page.tsx`.
- The work pages render out of `app/(app)/saints/[slug]/[work]/page.tsx` and pick up the same TOC sheet, font controls, mobile top bar, and per-paragraph highlight/note/bookmark gestures already shipped.
- The per-verse commentary cards in the Bible reader's study rail (and the mobile commentary sheet) automatically pull any new `data/commentary/{book}/{chapter}.json` entry whose `author` is mapped in `lib/saints/icons.ts` — that's the merge-not-clobber behavior from v3.10. Theophylact's icon and attribution would show up in the rail beside Matthew, Mark, Luke, and John verses the same Sunday the data lands.

**Open question.** Editorial choice on whether to ship Theophylact-on-John alongside the existing Chrysostom-on-John, or behind a per-Father toggle in the commentary rail. Recommend ship-alongside; the chain-of-Fathers reading pattern is what the site already does best.

## 📅 4. Regional Patriarchate Calendar Matrix

**System Architecture.** The current `/calendar` already has a binary toggle (`New (Revised Julian)` vs `Old (Julian)`) driven by `lib/calendar/orthodox.ts`. The community ask is to add a *jurisdictional* axis on top of the reckoning axis, because two jurisdictions on the same reckoning can still commemorate different saints on a given day.

Decouple the page from a single global rule:

- **Define a `CalendarMatrix` type** in `lib/calendar/matrix.ts`:
  ```ts
  type CalendarMatrix = {
    slug: "ecumenical" | "moscow" | "constantinople" | "antiochian" | "serbian" | "rocor" | ...
    title: string
    reckoning: "new" | "old"
    menologionRef: string // points at data/calendar/menologion-{slug}.json
    fastingRulesRef: string // points at data/calendar/fasts-{slug}.json
    paschaShared: true // always true; Pascha is canonical across all
  }
  ```
- **Data files.** Today's `data/calendar/daily-saints.json` becomes the *base* menologion (ecumenical-Greek-leaning, since that's what shipped first); each jurisdictional matrix adds its overrides in `data/calendar/menologion-{slug}.json` as a *patch* (saints added, saints reordered, headline commemoration swapped). At read time the calendar layer composes `base + patch` per active matrix — same merge-not-clobber pattern as the commentary rail.
- **Pascha stays one calculation.** All canonical churches keep the same Pascha; only the fixed feasts and saints differ. The existing Pascha algorithm is untouched.
- **Fasting rules.** Russian and Greek practice diverge on details (cheesefare nuances, oil/wine allowances on specific feasts). Same patch model: `fasts-{slug}.json` overrides for the matrices that need it; default rule used otherwise.

**UI/UX (preserving the menologion register from v5.2).**

- The current Old / New toggle stays. A second small inline control beside it: `Tradition · Greek / Russian / Antiochian / Serbian / ROCOR`. Same gold-underlined-active-label, dot-separator treatment so it visually belongs to the same row. Avoid a dropdown — five-or-six matrices fit as inline labels on desktop; on mobile they collapse into a single sheet behind a "Tradition" pill.
- A single-line italic note appears under the hero when a non-ecumenical matrix is active: *"Showing the Russian Orthodox menologion. Pascha is shared."* Disappears for the default.
- The illuminated drop cap and rubric red treatment from v5.2 work unchanged — only the *content* of the saint name and fast label changes between matrices.

**Local Storage / Account Sync.**

- **Persist locally.** Mirror the existing pattern for the Old/New toggle: write `purify_calendar_tradition` and `purify_calendar_reckoning` to `localStorage`, and mirror both to cookies so the server-rendered `/calendar` page reads them on first paint without a flash of wrong content (the calendar reckoning cookie pattern from v5.4 already does this; the tradition cookie is one more line).
- **Sync to public account.** Add two columns to the existing `profiles` table: `calendar_reckoning text default 'new'` and `calendar_tradition text default 'ecumenical'`. Existing client-side prefs sync (debounced 500ms push, on-mount pull) added in v3.3 picks these up automatically once the column names are in the `PROFILE_PREFS` allowlist.
- **Migration.** One SQL migration `supabase/migrations/{ts}_profiles_calendar_tradition.sql`. Backfill any existing row to `'ecumenical'`. RLS already covers `profiles`; no new policies needed.

**Open question.** Editorial labor: each new tradition needs a vetted menologion patch. Suggest shipping the engineering scaffolding first with just the ecumenical matrix in place, then bringing on one matrix at a time as the editorial work completes — same incremental pattern the saints registry used.
