# Internationalization (i18n)

Per `docs/prd/v6.4-community-feedback.md` §2. Two tracks:

- **Track A — UI chrome localization.** Navigation, button labels, eyebrows, error strings, FAQ, About, prayer-rule scaffolding. Texts themselves (Scripture, Fathers) stay in their published languages. Roughly ~1,200 strings once fully extracted.
- **Track B — Liturgical / textual localization.** Surface the Scriptures and prayers in Greek and Slavonic / Russian. Content acquisition problem; one corpus + editorial pass per language.

## Phases

1. **Phase 1 — Engineering only. *Partial, shipped in v6.4.*** Locale registry, message catalog format, server-side loader. **No route restructure yet.** Catalogs are callable but not wired into the page tree.
2. **Phase 2 — Route restructure + Spanish UI chrome.** Move every page under `app/(app)/...` to `app/[locale]/(app)/...`. Add middleware that reads `accept-language` on first visit, persists to a `purify_locale` cookie, and serves the matching locale segment thereafter. Extract all hard-coded strings into the English catalog, then translate to Spanish. **Out of scope for v6.4.**
3. **Phase 3 — Greek liturgical.** NT Greek display toggle + Greek UI chrome at `/el`.
4. **Phase 4 — Russian.** Synodal Bible + Slavonic prayer set at `/ru`. Largest content lift.

## What ships in v6.4

- `lib/i18n/locales.ts` — typed `Locale` + `LocaleCode`, `LOCALES` registry, `DEFAULT_LOCALE` constant, `resolveLocale()`, `negotiateFromAcceptLanguage()`, `isLocaleReady()`.
- `lib/i18n/index.ts` — `getMessages(locale)`, `t(messages, key)`. Reads JSON catalogs.
- `lib/i18n/messages/{en,es,el,ru}.json` — flat-key catalogs. English ships a starter ~25-key set covering nav, common buttons, calendar, and the footer doxology. The other three locales ship as empty objects (`{}`) and fall back to the English catalog when keys are missing.

This is enough for contributors to extract strings into the catalog *as they touch each page*, instead of needing one big extraction PR before any translation can begin.

## How to extract a new string

1. Find the string in a component, e.g. `<p>Save changes</p>`.
2. Add a key to `lib/i18n/messages/en.json`, e.g. `"common.saveChanges": "Save changes"`.
3. Replace the literal in the component with `t(messages, "common.saveChanges")`. The `messages` value comes from a server component calling `getMessages(locale)` once at the top of the page, and is threaded down via a single context provider (this provider lands when the route restructure ships in Phase 2).

For now, only Phase 1 — the registry and the loader — is in place. Components continue to use literal strings until Phase 2 begins the route restructure.
